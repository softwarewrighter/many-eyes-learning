1) Exploring Reasoning Reward Model for Agents (Reagent / Agent-RRM)
What problem they’re attacking
Agentic RL often uses sparse, outcome-only rewards (“did you solve the task?”). That’s brutal for long-horizon tool-using agents: it can’t tell the difference between “almost right, failed at the end” and “complete nonsense.” 

Core idea (what’s novel)
They build a Reasoning Reward Model for agents (Agent-RRM) that emits structured feedback for an agent trajectory:

an explicit reasoning trace (<think>)

a targeted natural-language critique (<critique>)

an overall scalar score (<score>) 

Then they test three ways to inject that feedback into an agent training/inference loop:

Reagent-C: critique-driven text refinement (use the critique to revise/repair reasoning)

Reagent-R: reward-driven guidance (use reward signal to steer learning)

Reagent-U: unified integration (combine all signals) 

Claimed outcome: strong gains across a bunch of benchmarks (they cite GAIA, WebWalkerQA, etc.). 

How the GitHub repo is organized (what you can actually run)
The repo is kxfan2002/Reagent and includes:

a unified evaluation framework under Evaluation/unified_eval (per README) 

scripts/examples for setting up reward model servers, data prep, and training (e.g., examples/reagent/reward_model.sh, prepare_data.py, train.sh) 

it explicitly notes the reward model servers “require multiple GPUs” in their quickstart flow 

Pros / what it’s good for
Dense-ish supervision without hand-labeling every step: if the reward model is good, you get shaped feedback that’s closer to “process reward” than “final-answer reward.” 

Actionable textual critique is useful even without full RL training—could be used at inference-time for self-repair (their Reagent-C framing). 

Research substrate: they say code/models/datasets are released; repo README points to hosted artifacts. 

Cons / caveats (the “reward-models bite back” section)
Reward hacking risk doesn’t vanish—it moves: now the agent can optimize for what the reward model likes, not what reality wants. The paper itself flags reward hacking as a known issue in this space. 

Compute complexity: running reward-model servers (potentially multi-GPU) + agent training + evaluation harness is non-trivial. 

Calibration & distribution shift: a reward model trained on one style of trajectories/tools can mis-score novel tools/environments.

Text critiques can be persuasive nonsense: you’ll want audits/ablation checks so the critique isn’t just “confident fanfic.”

How to “try it” quickly (practical path)
Start with their evaluation harness first (cheapest way to learn what’s going on): Evaluation/unified_eval, configure a model endpoint, run a small subset benchmark. 

Only then attempt the heavier pipeline: reward model server → data prep → training scripts. 

2) Intrinsic Reward Policy Optimization for Sparse-Reward Environments (IRPO)
What problem they’re attacking
In sparse reward RL, the true policy gradient is basically uninformative most of the time (no reward signal → no gradient signal), so exploration + credit assignment are painful. 

Core idea (what’s novel)
They propose IRPO, which uses multiple intrinsic rewards to train exploratory policies, then uses the extrinsic reward discovered by those explorers to update a base policy via a surrogate gradient (“IRPO gradient”) constructed by backpropagating through the exploration updates (chain rule / Jacobians). 

In their arXiv HTML, Algorithm 1 lays out the structure:

update exploratory policies using intrinsic rewards

compute/store Jacobians relating base → explorer updates

compute extrinsic policy gradients of explorers

combine them into the IRPO gradient to update the base policy 

They mention using diffusion-maximizing intrinsic rewards (at least in this work), but the framework conceptually supports other intrinsic rewards. 

What’s in the GitHub repo (what you can run)
The official code is Mgineer117/IRPO (linked from the paper). 

The README gives a simple entry point:

create conda env (Python 3.11)

pip install -r requirements.txt

train via: python3 main.py --env-name pointmaze-v1 --algo-name irpo 

It also supports logging to W&B, TensorBoard, CSV, and saves model params/best checkpoint. 

Pros / what it’s good for
More informative learning signal in sparse-reward settings by explicitly leveraging “explore-with-intrinsic, learn-with-extrinsic” in a gradient-connected way. 

Modular intrinsic rewards: you can swap in different intrinsic reward functions (in principle). 

Repo looks relatively straightforward to run compared to giant agent stacks: one main training command, standard logging. 

Cons / caveats
Bias in the surrogate gradient: they explicitly call it a surrogate; anytime you replace the “true” gradient, you’re trading bias for signal. 

Stability + hyperparameter sensitivity: multi-policy systems (base + explorers) tend to have knobs (how many intrinsic rewards, how you weight them, update schedules).

Compute overhead: multiple exploratory policies + critics can multiply runtime/memory.

How to “try it” quickly
Run their baseline training command on a single environment (pointmaze-v1) and log to CSV/TensorBoard first. 

Then vary:

number/types of intrinsic rewards

number of exploratory policy updates per base update

whether you can reproduce their reported sample-efficiency improvements

Comparing the two (useful mental model)
They rhyme, but they’re not the same beast:

Reagent / Agent-RRM: “Let’s make feedback richer for agent trajectories (including natural language critique) and use it to improve reasoning/tool use.” 

IRPO: “Let’s make gradients less useless in sparse reward RL by routing extrinsic reward through intrinsic-reward-driven exploration.” 

If you’re thinking about building systems (not just papers):

Reagent is closer to LLM-agent training/eval infrastructure + reward modeling.

IRPO is closer to core RL algorithm design for sparse rewards.

“If I were verifying this as an engineer” (sanity checks)
Reagent: try to reproduce one benchmark slice end-to-end; then ablate (score only vs critique only vs unified) and see if unified consistently wins like claimed. 

IRPO: reproduce learning curves on one discrete + one continuous task; confirm sensitivity to intrinsic reward choice and number of explorers. 

That’s the tour. The fun meta-lesson: both papers are basically saying, “Sparse signals are a tragedy; let’s smuggle in richer ones”—one via language-based reward feedback, the other via intrinsic-reward exploration gradients.

2) How many parallel agents do you actually need?
You don’t need 14 to demonstrate the concept. You need enough to show:

diversity of exploration (scouts cover different regions),

faster time-to-first-success (a scout finds the sparse reward sooner),

and base policy improvement over iterations.

Diminishing returns in demos (the boring truth)
In most exploration demos, the curve from “more scouts” looks like:

1 scout: slow, sometimes never hits reward in time window.

2–4 scouts: big improvement, clearly visible.

6–8 scouts: improvement continues, but less dramatic.

>8 scouts: mostly “cool swarm visuals” rather than learning breakthrough.

So for a YouTube Short and a clean explainer:

4 scouts is the minimum where it feels like “parallelism matters.”

8 scouts is the sweet spot: visually satisfying + clearly better statistics.

12–16 scouts is for flexing hardware, and it increases complexity and timing jitter.

Recommendation: Design the UI to support 1, 2, 4, 8 scouts as “preset buttons.” You can still have a “14 scouts” mode later.

3) Can two or more agents share a GPU?
Yes, but there are two different meanings of “share,” and only one is pleasant.

Sharing style 1 — Multiple processes / multiple model instances (usually painful)
You run multiple separate inference/training processes pinned to the same GPU.

Pros: Simple conceptually.

Cons: Memory fragmentation, context/KV cache blowups, unpredictable latency, and if they all generate tokens at once you get the “everyone stutters” effect.

This is how you end up “debugging GPU scheduling” instead of making a demo.

Sharing style 2 — One GPU server, many concurrent requests (recommended)
You run a single inference server per GPU and route multiple agent requests to it. The server handles batching/scheduling.

Pros: Predictable memory usage, better throughput, easier instrumentation.

Cons: Requires a server stack that supports concurrency/batching.

In your world this could be:

llama.cpp server per GPU, or

an Ollama instance per GPU host (if you’re using Ollama models), or

vLLM-style server if you go that direction (heavier), or

Candle-based Rust service (if you want Rust-native, but more work).

CUDA MPS (Multi-Process Service)
Because you mentioned P100/P40: these are datacenter-ish NVIDIA parts on Linux, and CUDA MPS is a real option to reduce context-switch overhead when multiple CUDA processes share a GPU.

Pros: Can improve multi-process concurrency.

Cons: Still doesn’t fix memory contention; still can produce jitter.

Demo recommendation: Prefer one “GPU worker service” per GPU and have scouts be “logical agents” multiplexed onto that service.

4) Heterogeneous GPUs: do you need to compensate for timing differences?
If you’re doing real learning updates and you expect synchronized steps, heterogeneous compute can create headaches (faster scouts produce more data; slower ones lag; batching windows skew).

But you can sidestep this with one simple design rule:

Make the coordinator “event-driven,” not “step-synchronized”
Scouts produce episodes/rollouts at their own pace.

Coordinator updates base policy on a schedule (e.g., every N episodes received or every T seconds) and logs everything.

UI visualizes what happened, including “scout throughput” per GPU.

Then heterogeneity becomes a feature you can show:

P40 scouts run X steps/sec, P100 scouts run Y steps/sec.

Yet the base improves faster with more parallel exploration.

So yes, you can use heterogeneous GPUs without compensation—as long as your algorithm loop is asynchronous.

# many-eyes-learning

**Structured exploration for better learning under sparse rewards**

---

Learning often fails not because models are slow, but because they see too little.

In sparse-reward problems, useful feedback is rare. A single learner exploring alone is likely to miss it entirely. When that happens, learning stalls—not due to lack of compute, but due to lack of information.

This project explores a simple idea:

> **Put many eyes on the problem.**

Instead of relying on one explorer, we use multiple exploratory passes—*many eyes*—to gather diverse information during training. What those eyes discover is then combined to improve learning outcomes.

The goal is **not speed**.  
The goal is **better learning through better information**.

---

## What “many eyes” means here

In this project, **many eyes refers to training-time exploration**, not inference-time assistance.

- Each “eye” is an exploratory run (a *scout*) with its own bias or exploration strategy.
- Scouts gather experience in environments where rewards are sparse.
- Their discoveries are aggregated to improve a shared learner.

Parallel execution is optional. Scouts can run sequentially or concurrently—the benefit comes from **diversity of exploration**, not wall-clock speed.

---

## What this project is (and is not)

**This project is:**
- About improving learning outcomes in sparse-reward settings
- About spending more computation *intelligently*, not faster
- About exploration as an information problem
- About simple, reproducible demos that run on modest hardware

**This project is not:**
- A benchmark shootout
- A GPU optimization project
- A claim about training speedups
- A requirement for parallel or distributed systems

---

## Why this matters

Sparse rewards create an information bottleneck. When feedback is rare, gradients are weak and learning becomes fragile or impossible.

Adding more exploration—*more eyes*—helps because it:
- reduces blind spots,
- increases coverage of the problem space,
- uncovers rare but valuable learning signal.

Better information leads to better learning.

---

## Project structure (high-level)

This repository contains:
- Minimal environments with sparse rewards
- Sequential and parallel exploration modes
- Aggregation strategies for scout experience
- Visualizations that reconstruct “many eyes” exploration
- Reproducible experiments demonstrating improved learning outcomes

The same code paths can run:
- sequentially on a laptop, or
- in parallel on larger systems

The results should be comparable—the difference is only wall-clock time.

---

## Relationship to research

This project is inspired by research on:
- structured exploration in sparse-reward environments,
- multi-policy exploration (e.g. scout-based methods),
- intrinsic motivation and information-driven learning.

The focus here is **clarity and intuition**, not exact reproduction of any single paper.

The problem is that learning is blind.*
